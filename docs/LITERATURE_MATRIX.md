# Rust-Boy | Evidence-to-implementation literature matrix

**Review snapshot:** 2026-10-24. **Evidence entries:** 37. Authoritative machine-readable index: [`catalog/literature.json`](../catalog/literature.json).

## Method

For continuously updated software documentation, the listed year indicates the **2026 review snapshot**, not a claimed first-publication year. Published papers and versioned standards retain their publication/version year.

This is an **engineering evidence matrix**, not a claim of systematic-review completeness. Sources were selected from peer-reviewed software-systems research, official language/library documentation, primary technical standards, and first-party policy statements. Search emphasis: Rust composition and dyn compatibility; local-first storage; human-interface testability; Linux/Raspberry Pi GPIO, serial and BLE; GNSS/geospatial formats; radio/ADS-B; cryptographic trust; secure build pipelines.

**Ranking:** peer-reviewed research (theoretical or empirical context); normative technical standards (protocol/data contracts); first-party API documentation (implementation options); provider policy/licensing (constraints). Distinguish the type of evidence from the level of confidence it can justify: a library page is not a validation study, and a protocol standard does not attest implementation security. Each row records a specific design implication, uncertainty, and test that could falsify a premature capability claim.

## Interpretation and conflicts

1. **Rust polymorphism:** object safety/dyn compatibility [L01, L02, L25] favors dynamic dispatch for a fixed internal module runtime; do **not** treat a Rust trait as a stable C/plugin ABI. Memory safety findings [L03] do not cover unchecked FFI or third-party device drivers.
2. **Local-first vs. synchronized data:** [L04] motivates device ownership and resilience. Peer replication is an optional G3/G4 research topic, not an excuse to enable background sync in G0.
3. **Offline maps vs. online community tile servers:** [L09–L11] support standards-based geometry and lawful map provenance. OSM's public raster tile policy explicitly forbids offline prefetch; offline bundles must come from licensed downloads, self-hosted datasets, or user-provided sources with verified rights.
4. **Sensor connectivity vs. permissions:** [L06–L08, L12–L14, L24] identify APIs and formats but cannot establish that a device is present. Replaying recorded fixtures is required before physical access; opt-in permission gates are separate.
5. **Receive-only radio vs. mesh messaging:** [L20, L23, L24] justify distinct RX-only SDR/ADS-B adapters. [L12, L15, L21, L22] inform cryptographic and transport requirements for peer messaging but do not establish a completed secure protocol.
6. **Testing and measured performance:** [L26–L27] support property-based tests and device-specific energy benchmarks; do not claim power efficiency by language choice alone.
7. **BLE mesh and ADS-B source reliability:** [L28–L30] add literature reviews and receiver-network case evidence, not an automatic approval to transmit or perform unconsented sensing.
8. **Access and supply-chain assurance:** [L05, L16–L18] call for real keyboard/contrast tests, reproducible CI checks, and build provenance. No WCAG or SLSA certification is asserted by the roadmap.

## Missing evidence to resolve before implementation

- Raspberry Pi display/controller pinouts and board revisions for the **specific selected** hardware SKU.
- Recorded, legally obtained SDR/ADS-B IQ and decoded frame corpora with provenance and regression tests.
- Measured CPU, latency and battery budget on Pi 5 / ARM64 for each active adapter.
- Selected local messaging transport and threat model, including peer identity, revocation, replay and key backup.
- A distribution license audit for fonts, sound, cartographic tiles and every native/FFI dependency.
- Measurable accessibility acceptance criteria for real terminal and wearable displays, beyond analogy to web WCAG.
