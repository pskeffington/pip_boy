# Rust-Boy | Overseer Task Control

**Implementation:** Task Control is a persistent, operator-managed offline mission board. Overseer now ships with `mission-board` as its first, preloaded module. The seven other job profiles still load their original tools and **Custom is last**. Other role HUDs receive a filtered local duty queue for work assigned to their job title. The Task Control module is available in Custom if explicitly pinned.

**Delivery boundary:** Task Control does **not** send email, authenticate other users, broadcast over TAK, or synchronize devices. A supervisor can prepare a copyable task handoff or explicitly open an email draft in the local mail client. Only the human can send it; Rust-Boy does not infer transmission or acceptance. "Mark sent" and "Record acknowledgment" are **manual logs**, not verified delivery or authenticated remote responses.

## Try it on a Mac

```bash
git clone --branch feat/overseer-task-ops https://github.com/pskeffington/pip_boy.git
cd pip_boy
./scripts/launch-micro.command
# Or for the desktop version:
cargo run --locked -p pipboy -- dashboard --open
```

On a new install Overseer is active. On an existing install, open the job template selector and explicitly **reload Overseer** if its old saved pins do not yet contain Task Control. This replaces only pinned modules; **tasks are stored in a separate file** and survive profile changes. In micro mode choose **STAT > OPEN TASK CONTROL** or **GEAR > TASK CONTROL**. On desktop, the Overseer **Module Viewport** shows the board.

## Management workflow

1. **Create an assignment:** Choose **+ NEW ASSIGNMENT**, enter title, short instructions, assignee, target job, priority, optional due date and optional recipient email. Create stores the task locally with status `todo`, revision 1 and an audit record. The assignment has **not** been sent.
2. **Manage queue:** Filter by Active, Overdue, Blocked, Done or All. Counts reflect locally recorded assignments, not a remote team. Overdue is evaluated against the browser's current local calendar date.
3. **Prepare handoff:** Open a task and select **PREPARE HANDOFF**. A bounded plain-text message with `RB-0001`-style reference, recipient, job, instructions, priority and due date is generated by Rust. Use **COPY ASSIGNMENT** to paste into your chosen secure channel, or **OPEN EMAIL DRAFT** to invoke the Mac's configured mail client. These two actions do not transmit anything themselves.
4. **Mark sent:** Only after deliberately sending outside Rust-Boy, click **MARK SENT (MANUAL)** and confirm. The board records a timestamp and event; actual delivery remains unverified.
5. **Acknowledge and track:** After receiving confirmation from the operator outside this application, manually **RECORD ACKNOWLEDGMENT**. Status progresses through To do / In progress / Blocked / Complete. A brief note may be added. Assignee changes reset delivery/acknowledgment flags and preserve history.
6. **Role queue:** Switch to e.g. **Head Engineer**, **Reclamation Scout** or **Security Chief**. Their micro STAT page shows tasks assigned to that job; **VIEW ASSIGNED DUTIES** opens the queue and allows status or acknowledgment updates on the same local device. A role switch **does not authenticate identity** or create a remote inbox. Other jobs do not get the Overseer's create/reassign controls.

**No fictitious data:** A new install starts with **zero tasks**. There are no pre-generated incidents, notifications, remote acknowledgments, or battery/GNSS readouts.

## Data and validation contract

```text
PIPBOY_HOME/
  workbench.json    # role/tiles only
  tasks.json        # durable task board (created on first accepted write)
  tasks.lock        # cooperative local writer lock
  notes.json        # separate notes store; never read for task listing
```

On macOS/Linux the directory is created with permission `0700` and the task file `0600`. The file uses an explicit v1 JSON schema, a maximum 512-KiB size and 256 tasks; up to 32 recent events per task are retained. Every update includes an **expected revision**, so concurrent or stale tabs receive HTTP 409 instead of silently overwriting newer state. Writes use a cooperative lock, a temporary file, an atomic rename and disk synchronization. Unknown/future schema and corrupt data cause an error **without resetting or overwriting** the original file. Task titles, assignees, notes, dates, roles and email contacts are bounded and validated. Plaintext files are **not encrypted** and should not contain confidential personal/medical/security records.

The service has no task-specific listener. It runs on the existing **127.0.0.1-only** dashboard server with exact Host and Origin restrictions, bounded same-origin JSON requests, CSP and no arbitrary shell endpoint.

| Endpoint | Access | Behavior |
| --- | --- | --- |
| `GET /api/tasks` | Local active role | Overseer/Custom with Task Control sees the board; other profiles see tasks filtered by assigned job |
| `POST /api/tasks/create` | Task Control pinned | Validate and create local task |
| `POST /api/tasks/change` | Task Control manager; or matching assigned role for status/ack | Update status, reassign, record manual sent/ack, with expected revision |
| `POST /api/tasks/handoff` | Task Control pinned | Return an operator-controlled plain-text handoff; no change to delivery state |

A workstation's role selector is **not an authentication boundary**. Any application running under the same OS account can read the plaintext task file, and a local person can select another job template. Do not treat a task's assignee or `acknowledged_at` as an identity-verified claim. True team delivery, recipient authentication, end-to-end acknowledgments, and cross-device sync require a reviewed authenticated transport, durable inbox/outbox with replay protection, encryption, revocation and authorized roster management.

## Exact acceptance pass

```bash
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo build --workspace --locked
node --check crates/pipboy/assets/tasks.js
python3 tools/smoke_tasks.py
```

The smoke test exercises an actual local Rust HTTP server, creates ten assignments, verifies handoff text does **not** mark a task sent, records manual send/ack/status changes, rejects revision conflicts and invalid fields, proves role-scoped queues and persistence, checks assets/CSP, and verifies no external-device permissions or notes stores are touched. It runs in Linux and native macOS/Windows CI.

**Next gates:** real operator identity and signed handoff packets, opt-in encrypted local mesh/LAN transport, incoming device inbox + acknowledgment receipts, escalation policies, task reminders and auditable report export. Do not mark any of these as complete in the R1 UI.
